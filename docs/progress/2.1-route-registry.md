# 🗺️ Progress 2.1 — Dynamic Route Registry

[← Back to GateFlow README](../../README.md) · [← Progress 1.5](1.5-request-metadata.md) · [Next: Progress 2.2 →](2.2-route-administration.md)

## Overview

This stage introduced the dynamic route registry, allowing GateFlow to determine which backend service should receive an incoming request.

Instead of hardcoding every forwarding decision into the gateway, routes are represented as configuration entries. The gateway uses the registry to match incoming request paths and identify the appropriate upstream service.

## Objectives

- Create a centralized route registry.
- Register multiple backend service routes.
- Match incoming requests against configured paths.
- Support path-prefix stripping.
- Validate HTTP methods against route configuration.
- Support longest-prefix matching.

## Architecture

```text
Incoming Request
       |
       v
Route Registry
       |
       v
Find Matching Route
       |
       |-- No match --> Route Not Found
       |
       v
Longest Prefix Match
       |
       v
Validate HTTP Method
       |
       |-- Invalid method --> Method Not Allowed
       |
       v
Resolve Upstream Service
       |
       v
Reverse Proxy
```

## Implementation Details

The route registry is located at:

`gateway/core/route_registry.py`

Known route configuration fields include:

| Field | Purpose |
|---|---|
| `name` | Unique route identifier |
| `path` | Public gateway path |
| `service_url` | Destination backend service |
| `strip_prefix` | Prefix removed before forwarding |
| `methods` | Allowed HTTP methods |

Example route configuration:

```json
{
  "name": "product-route",
  "path": "/api/products",
  "service_url": "http://product-service:8003",
  "strip_prefix": "/api",
  "methods": ["GET"]
}
```

### Longest-prefix matching

When multiple route paths could match a request, the registry uses the most specific matching prefix.

For example:

```text
/api/products
/api/products/categories
```

A request to `/api/products/categories` should match the more specific route when both routes are registered.

### Method validation

The registry checks the incoming HTTP method against the methods configured for the matched route.

This prevents a route configured for GET from automatically accepting unsupported methods.

### Prefix stripping

The `strip_prefix` configuration allows the gateway to remove a public path prefix before forwarding the request to the upstream service.

For example, the public path:

```text
/api/products
```

can be forwarded to the Product Service with the `/api` prefix removed.

## Verification and Testing

The following route behavior was verified during development:

- User Service route matched `/api/users`.
- Product Service route matched `/api/products`.
- Requests were forwarded to the corresponding services.
- Route matching supported path-prefix behavior.
- HTTP methods were checked against route configuration.

The gateway's route listing endpoint was also used to inspect registered routes:

```bash
curl http://localhost:8000/gateway/routes
```

Suggested additional checks:

- Register overlapping routes and verify longest-prefix behavior.
- Test unsupported methods.
- Test requests that do not match any route.
- Test trailing-slash and URL-encoding edge cases.

## Result

GateFlow now has a centralized dynamic route registry. This separates route configuration from proxy execution and makes it possible to manage gateway routes without embedding every service mapping directly into request-handling logic.
