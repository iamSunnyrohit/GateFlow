# 🧩 Progress 1.4 — Microservices Integration

[← Back to GateFlow README](../../README.md) · [← Progress 1.3](1.3-reverse-proxy.md) · [Next: Progress 1.5 →](1.5-request-metadata.md)

## Overview

This stage connected GateFlow to two independently running backend services: User Service and Product Service. The gateway can route client requests to these services while keeping their internal container addresses out of the client-facing API.

## Objectives

- Create separate User and Product service applications.
- Run the services as independent Docker Compose services.
- Connect each service to the gateway through configured routes.
- Verify that gateway requests reach the correct upstream service.

## Architecture

```text
                  Client
                    |
                    v
             GateFlow Gateway
                :8000
               /      \
              /        \
             v          v
       User Service  Product Service
          :8002          :8003
```

The service ports `8002` and `8003` are container ports used by the gateway within the Docker Compose network. The gateway is exposed on host port `8000`.

## Implementation Details

The service directories are:

- `backend-services/user-service/`
- `backend-services/product-service/`

Each service has its own application module, `requirements.txt`, and Dockerfile.

Known route configuration:

| Public gateway path | Upstream service | Internal service URL |
|---|---|---|
| `/api/users` | User Service | `http://user-service:8002` |
| `/api/products` | Product Service | `http://product-service:8003` |

Both routes were configured for GET requests and use `/api` as the prefix to strip before forwarding.

Observed responses during development included:

- `GET /api/users` returned a User Service response with three sample users.
- `GET /api/users/1` returned the sample user Rohit.
- `GET /api/products` returned a Product Service response with three sample products.
- `GET /api/products/1` returned the MacBook Pro sample product.

These are development fixtures and should not be interpreted as production data.

## Technologies

| Technology | Role |
|---|---|
| Python | Service implementation |
| FastAPI | Backend service APIs |
| Docker | Service containers |
| Docker Compose | Service orchestration |
| HTTPX | Gateway-to-service forwarding |

## Verification and Testing

The following gateway-to-service calls were verified during development:

```bash
curl http://localhost:8000/api/users
curl http://localhost:8000/api/users/1
curl http://localhost:8000/api/products
curl http://localhost:8000/api/products/1
```

The gateway successfully returned responses from both upstream services.

Suggested additional checks:

- Stop one service and observe the gateway's upstream-failure behavior.
- Confirm services are not unintentionally exposed on public host interfaces.
- Add automated integration tests for both route mappings.

## Result

GateFlow now demonstrates a multi-service architecture: clients call the gateway, and the gateway forwards requests to the appropriate backend service.
