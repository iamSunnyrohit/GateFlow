# 🔀 Progress 1.3 — Reverse Proxy

## Overview

This stage introduced asynchronous reverse-proxy behavior to GateFlow. The gateway receives a client request, selects a destination service through the routing layer, and forwards the request rather than requiring the client to know the internal service address.

This creates a single client-facing entry point while allowing backend services to remain independently deployed.

## Objectives

- Forward incoming HTTP requests to backend services.
- Build the upstream URL using the configured service URL and request path.
- Preserve the incoming query string.
- Forward relevant request headers.
- Avoid forwarding hop-by-hop headers that should not pass through a proxy.
- Use the shared asynchronous HTTPX client.

## Architecture and Request Flow

```text
Client request
     |
     v
GateFlow Gateway
     |
     v
Route selection
     |
     v
Proxy forwarding (HTTPX)
     |
     v
Destination microservice
     |
     v
Gateway returns upstream response
```

## Implementation Details

The proxy implementation is located at `gateway/core/proxy.py`.

Known implementation details:

- The forwarding function is named `forward_request`.
- It builds a target URL from the service URL, route path, and incoming query string.
- It uses HTTPX's asynchronous request functionality through the shared client.
- It filters hop-by-hop headers before forwarding.
- Redirect following is disabled on the shared HTTPX client.

The known hop-by-hop header filter includes:

```python
HOP_BY_HOP_HEADERS = {
    "connection",
    "keep-alive",
    "proxy-authenticate",
    "proxy-authorization",
    "te",
    "trailer",
    "transfer-encoding",
    "upgrade",
    "host",
}
```

The proxy layer works alongside the route registry. Route selection and prefix-stripping behavior are configured in the routing layer; the proxy is responsible for forwarding to the selected upstream.

## Verification and Testing

Development checks confirmed that requests sent through the gateway reached the configured User and Product services.

The following endpoints were tested:

```bash
curl http://localhost:8000/api/users
curl http://localhost:8000/api/users/1
curl http://localhost:8000/api/products
curl http://localhost:8000/api/products/1
```

Suggested additional checks:

- Test forwarding of request bodies for write methods.
- Test query strings containing repeated parameters and encoded characters.
- Test upstream timeouts and connection failures.
- Verify response-header filtering and streaming behavior for large responses.

The suggested checks above should not be described as completed tests unless they are run and recorded.

## Result

GateFlow gained the core reverse-proxy capability required to route client traffic to independent backend services through one gateway endpoint.
